Summary

One marketplace for athletes, parents, coaches, brands, camps and agents.

WePulse is a marketplace and network for sports NIL (name, image and likeness) deals. Athletes, parents, coaches, brands, camps and agents use one sign-in to find each other, agree deals, sign contracts and get paid. An admin console runs verification, moderation and operations. A separate service, P Score, rates each athlete's marketability from 0 to 999.

03

FitMatch

A 3D body scan inside the athlete profile.

FitMatch produces about 70 athletic measurements, such as wingspan, height, predicted adult height, lean mass, body-fat percentage, BMI and limb circumferences, plus a rotatable 3D model. It supports recruiting and brand decisions and is not clothing sizing. The scanning partner holds the scan data and model; WePulse stores measurements and metadata.

P Score

A 0 to 999 marketability index computed by a separate service.

Every athlete gets a 0 to 999 marketability score that brands and agents can compare.

Composite score out of 100, multiplied by ten and capped at 999. Seven tiers map scores to labels from Youth/Grassroots to Global Superstar, with indicative value bands.

Architecture

How the apps, API, data and vendors fit together.

One GraphQL API is the single source of truth for the mobile app, web hub, brand dashboard, admin console and the P Score engine.

10.1System context

10.2Runtime behavior

  • Sign-in: every client signs in with Cognito; the API verifies the token and reads the user's groups.
  • Permissions: every operation has an explicit rule, anything without one is denied, and a build check fails if a rule is missing.
  • Real time: WebSocket chat and presence plus a notification subscription, backed by Redis publish and subscribe.
  • Background work: about 14 scheduled jobs guarded by Redis locks, plus workers for journey reels and video transcode.
  • Resilience: circuit breakers on vendor calls, retries, idempotent webhooks and rate limits.
  • Private networking: the API reaches P Score over private DNS; the admin console uses private links.

Security

Protection for payments, minors, data and infrastructure.

Deny-by-default permissions, child-privacy controls, signed payments and layered cloud protection.

13.1Controls

  • Deny-by-default permissions with a build gate on coverage; query depth and complexity limits; introspection off in production; Redis rate limits; a firewall on the API.
  • Child privacy: parental consent by e-signature with parent-before-minor ordering, custodial payouts, data minimisation, a 12-month retention sweep and birthdate attestation limits.
  • Payments: signed, idempotent webhooks; circuit breakers on about a dozen vendor calls; redaction of keys and personal data in logs.
  • Cloud: organization policies (region lock, root-user deny, MFA for sensitive actions), identity center tiers, break-glass role, organization audit trail, GuardDuty and Config in production, public access blocked on storage, Object Lock and dedicated keys for legal documents, short-lived deploy identities.
